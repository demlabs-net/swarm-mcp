# Telegram: вложения и доставка маркетинговых материалов

## До действия
1. Прочитай текущую задачу SLC, бриф, версию и согласования. «Покажи» разрешает показ запрошенного материала оператору, но не публикацию в каналах или рассылку партнёрам.
2. Проверь реальный каталог `telegram_reply` своей роли. Ниже контракт исходников swarm-mcp 0.6.3; при расхождении с runtime не угадывай параметры, сообщи расхождение.
3. Адресат — последний входящий Telegram-чат/топик **этой роли**. Без её истории используется настроенная общая группа. Параметров `chat_id`/`thread_id` в tool нет. Если допустимый адресат не установлен или файл приватный, не отправляй наугад; передай Надзирателю для согласованной доставки. Результат сообщает `chat_source` (`role_chat`/`group`) и `chat_id`, но это уже результат постановки в очередь, не безопасный предварительный просмотр адресата.

## Входящие файлы
- Найди фактический путь из заметки о вложении или доступной истории. Используй реально доступные инструменты поиска/чтения; не выдумывай сигнатуры `session_search`/`search_files`.
- Проверь существование, доступность, размер, формат и содержимое файла. Для изображений открой визуально: имя и заголовок PNG не подтверждают правильность логотипа или макета.
- Сохранение может завершиться ошибкой. Отсутствие заметки не доказывает отсутствие вложения. Сообщи проверенный факт («по указанному пути файла нет/не читается»), сохрани блокер, предложи повторную передачу при необходимости. Не говори, что шлюз всегда сохраняет файлы.
- Не переименовывай чужой логотип в DemLabs/Cellframe. Не генерируй логотипы; используй предоставленные/одобренные активы с источником и областью применения.

## Подготовка результата
- Проверь бриф: канал распространения и площадка события — разные поля. Размеры, языки и число обложек бери из текущего задания, а не из прежних AMA.
- После правки макета заново выполни рендер доступным проверенным инструментом. Проверь каждый фактический экспорт: текст, дату/часовой пояс, активы, поля, читаемость, размеры.
- Сохрани/скопируй только разрешённый результат в общую папку, видимую агенту и swarm-mcp как `/opt/data/inbound`. Приватный `/opt/data` агента и путь хоста не обязательно видимы серверу. Проверь содержимое после копирования; не обходи ограничение симлинком наружу.

## Контракт `telegram_reply`
Предпочитай `files[].path`, не перенос длинного base64 через ответ модели и не прямые HTTP-вызовы с извлечением токенов.

```json
{
  "message": "Черновик на проверку — 1/1, русская версия",
  "files": [
    {
      "filename": "ama_ru_v2.png",
      "mime_type": "image/png",
      "path": "/opt/data/inbound/ama_ru_v2.png"
    }
  ]
}
```

Это пример структуры, а не утверждение существования файла или одобрения AMA. Подставь проверенный путь/версию.

- `message` — необязателен при наличии файлов; без файлов нужен непустой текст. Максимум задаётся runtime `max_message_chars`, не фиксированным числом из старой шпаргалки.
- `files` — максимум **5** объектов по схеме. `filename` обязателен (1–255 символов); `mime_type` до 100; `path` 1–1024 символа.
- Сервер принимает абсолютный путь внутри настроенной общей папки или относительный путь от неё, канонизирует путь, отклоняет выход за корень/не-файл. Лимит чтения по пути — **20 × 1024 × 1024 байт на файл**. Это не гарантия принятия фото Telegram: у Telegram дополнительные ограничения изображения; проверь результат доставки.
- Альтернатива для маленького файла: `content_b64`, 1–8 000 000 символов по схеме. Это не «8 MB исходного файла». Не задавай одновременно `path` и `content_b64`; используй путь, если он доступен.
- `image/*` отправляется как фото; остальное — документ. Текст становится подписью первого файла. Если требуется передать исходное изображение без фото-преобразования, согласуй подходящий документный формат (например архив), не обещай сохранение байтов фото.
- MEDIA-маркеры не отправляют файл через этот инструмент. Не включай такие маркеры в сообщение. Нет обязательного правила «сжимать до 45 KB» или «отправлять только по одному»; разделяй по смыслу и лимитам, нумерация должна совпадать с фактическим количеством.

## Проверка доставки и SLC
- `ok:true, queued:true` означает постановку в outbox, **не** доставку и не одобрение. Проверяй доступный `swarm://outbox`, ошибки/подтверждение отправки. Не повторяй отправку вслепую после таймаута — сначала исключи дубль.
- В SLC зафиксируй task ID, файл/версию, кому/что разрешено отправить, результат (очередь/доставлено/ошибка) и доказательство. COMPLETED допустим только при выполненных критериях, включая требуемую доставку.
- Согласования, необходимые команде, храни в `marketing_approval_register` с источником и областью, без посторонних приватных фактов. Одобрение макета не означает разрешение публикации.
- Менеджер пользуется `dispatch_to`/`dispatch_all`, работник `msg_to` по реальному каталогу/ACL. Swarm — транспорт, SLC — задачи; используй SLC delivery envelope, если требуется текущим сервером. Никаких выдуманных order/report.

## Старые references
Файлы references этого скила — исторические заметки, не актуальный транспортный контракт. Не следуй их примерам base64/direct HTTP/MEDIA, произвольным 5/8 MB лимитам, фиксированным размерам AMA или обещанию надёжного получения вложений. Для дизайна используй только правила, подтверждённые текущим брифом и реестром активов. Каталог runtime и правила выше имеют приоритет над историческими примерами.
